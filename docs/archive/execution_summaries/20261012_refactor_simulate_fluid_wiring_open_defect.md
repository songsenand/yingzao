# 执行摘要：simulate_fluid 工具层接线——内核已验，工具层发现系统性缺陷（**未发布为 canonical**）

## 动机
> 批次 4 第一半在上一轮完成（MPM 内核迁 Python 并数值验证）。本轮把 `simulate_fluid` 的
> **运行环**（驱动 + SDF 投影 + 守恒审计 + 快照）也接进 worker，并**重跑 `accept-m4`（24/24）**。
> 结论是**负面但重要**的：内核忠实，运行环在**高粒子密度**下出现系统性输运差异，
> 因此**Python 路径没有成为 canonical**，工具继续用 TS 实现，Python 路径退到显式开关之后。

## 具体操作步骤
> 1. 定义三个二进制交换文件（SDF 场+掩码+法向 / 种子阵 / 快照），大载荷按文件走 —— 既符合
>    "大载荷走文件"，也符合 Q1=B"文件即契约"。564k 粒子时种子文件 13.5 MB、单张快照 6.8 MB。
> 2. Python 侧实现运行环：标定 → EOS/粘性按 `rd/RD0` 缩放 → 近表面掩码（带 2.5·dx）→
>    逐步 `step + project + 出口计时 + 分速 + 快照` → 末态穿透/速度统计 → 写快照文件。
>    投影改用**向量化三线性采样**（逐粒子 Python 循环连超时都过不去）。
> 3. TS 侧只留 SDF 构建（`buildSdfFromStl`）、种子选择（`seedPositions`）、种子统计与警告、
>    存版与渲染。

## 预期风险与验证（关键：跑出来的两个问题）

### 问题 A：性能实测 **7×**，超出用户批准的 2.5–4×
> 真实工具场景（92×22×22 网格、13,680 粒子、200 步）：TS **1.47 s** vs Python **10.6 s** =
> **7.2×**。两次优化都无效（每 tap 合并三轴 bincount：7.05→7.29×；每轴权重只算一次：
> 7.29→7.21×），剖析显示成本在内核的**内存流量**（bincount 散射与 27 次 fancy indexing），
> 不是调用次数。**这超出你 2026-10-08 批准的量级**，原生 Rust/C 内核（实测比 TS 快 3.7–4.6×）
> 从"中后期"变成了这个工具的**实际必需项**。

### 问题 B：运行环在高密度下系统性输运不足（因此**未发布**）
> - **内核是忠实的**：`accept-mpm-parity` 全过（聚合量 Δrel 1e-8~1e-7、40 步后逐粒子
>   max|Δpos| 4.9e-6 mm）；追加的**纯内核跨密度检查**（2k/8k/20k 粒子 × 200 步，无 SDF/无入口）
>   **每一位都相同**（0.3408/0.3408、0.8435/0.8435、0.1618/0.1618）。
> - **低密度场景也对**：`accept-m4` case 1（11,799 粒子）到达率 **0.705**（TS 0.72，阈值 ≥0.7✓），
>   零穿透✓、守恒 0✓、不分叉✓、20/20 分速带流✓、整体 `pass`✓。
> - **高密度场景不对**：case 1b（38,394 粒子）到达率 **0.098**，TS 是 **0.8643**（阈值 ≥0.75）——
>   而且 TS 对该场景的**种子密度 ±1% 扰动完全不敏感**（三次都是 0.8643），说明这不是混沌抽样，
>   是**系统性差异**。90° 弯管同理：**0.12** vs TS **0.63**。
> - 运行环里**唯一未被内核 parity 覆盖**的环节是 **SDF 投影**，因此它是最可疑的一处
>   （已把"下一步：先禁用投影做二分"写进代码注释与矩阵）。
> - **处置**：`accept-m4` 在 TS canonical 下**重新全过**（弯管 0.7423、case1b 0.8643），
>   工具保持正确；Python 路径由 `DSH_CAD_FLUID_PYTHON=1` 显式开启，供后续定位。
>   **宁可让迁移停在这一步，也不静默发布一个错的流场。**
> - 回归：`accept-m4` PASSED、`accept-fluid-sign` OK(16)、`accept-mpm-parity` 全过、
>   `accept-tool-scope` OK、`tsc` 干净。
