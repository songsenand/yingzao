## 1. 流体仿真：从「看起来在流」到「能证明在管内流」

### 1.1 用户现象与实锤

用户原话：「对一个管道仿真，发现流体从管道外边跑的」。

复现（Ø60 / 内孔 Ø30 / 长 100，dx=2，6 粒子/格）：

| 项 | 数 |
|---|---|
| 种子格点总数 | 13,243 |
| 起点在管外（r > 30） | **3,648（27.5%）** |
| 最远起点半径 | 37.4 mm（管外 7.4 mm） |
| 起点在内腔（r < 15） | 9,595 |

根因不是求解器，是**种子域**：`deriveFluidPreset` 用包围盒取截面（54×54 的方块），
圆管的四个角既不是固体、也离壁很远，旧的「固体 + 离壁 0.75 mm」两条判据全部放行。
这四分之一粒子从第一步就在管外，之后沿外壁流、在出口平面被计入「到达」，
外观上就是「流体从管子外边跑」。旧报告没有「管外」这个指标，穿透只数
`sdf < -0.3`（在金属里），所以一直是 pass。

### 1.2 本轮已落地（2026-11-26）

| 改动 | 证据 |
|---|---|
| 种子只取**部件包围盒内的连通空洞分量**，且只取种子域中心所在分量 | `buildVoidComponents`；Ø60/Ø30 的 `rejectedOutside` = 3,648 |
| 端面所在格层按 `sdf ≤ 0.5·dx` 阻塞，避免沿端面把内腔与外部空气连通 | 未阻塞时内腔中心与盒角同为分量 1；阻塞后 3 vs 1 |
| 新增 `metrics.outsideSnapshotMax`：快照里「离金属 > 半格、但不在种子分量」的粒子数 | 旧实现无此数；现在 >0 即 `check` |
| `seedStats.rejectedOutside` 与 `overallStatus`、warning 联动 | `simulate_fluid` 描述与 [TOOL-CONTRACTS](../dsh-cad-harness/docs/TOOL-CONTRACTS.md) 已更新 |
| 验收 | `accept-fluid-sign` 21/21；`accept-m4` 全过（含 90° 弯头 c3 pass） |

诚实边界：本轮**没有**做粒子级的「穿壁后拉回」。种子不再在管外，但薄壁穿隧仍会发生。

### 1.3 新暴露的两个问题（比原缺陷更值得排）

1. **壁厚 < 2 格会漏，且必须报出来。**
   Ø34 / 壁 2 mm / dx=2（1 格壁）：`outsideSnapshotMax` = 707，`overallStatus` = check。
   旧实现因为 27.5% 的种子本来就在外面，反而「看不见」这种漏。
   出口：给 `simulate_fluid` 一条壁厚分辨率政策——要么自动把 dx 降到壁厚/2
   （代价是粒子数 ×8），要么在 `wall < 2·dx` 时直接拒绝并说明；验收用 1/2/3 格壁三档。
2. **`deriveFluidPreset` 的流轴 = 包围盒最长轴，短粗件会选错。**
   Ø44 / 长 30 的管，最长轴是 Y，于是沿横截面驱动，审计报 46 个管外粒子。
   出口：改为「过质心的最长空腔行程」或让用户显式给 inlet 轴；验收加一个长径比 < 1 的管。

### 1.4 还没做的（进 TODO F1/F2）

- 穿壁后的粒子级约束（回到种子分量 / 子步 / CCD），以及入口回流边界。
- 多入口、多出口、开口容器（自由液面）——现在的「闭合流道」语义不覆盖。
- 收敛性：dx 减半时 `outsideSnapshotMax`、`outletArrivalRatio` 的变化曲线。

## 2. 视口：零件颜色标识挤占视图 + 轴不可操作

### 2.1 证据（代码 + 语料）

- 冰雪城堡 r085 的运动回放有 **42 个零件实例**。`playback.ts` 的图例是
  `display:flex; flex-wrap:wrap; width:100%` 的一排 chip，每个含 8 px 色点 + 零件名
  （11 px）。在 400–600 px 宽的面板里约 6 排、~120 px 高；`PlaybackFrame` 的视口是
  `flex:1`，图例每多一排，3D 视口就少一排。用户看到的「能看到零件的区域很少」就是这个。
- 图例同时是显隐开关，但**没有**搜索、没有「只看运动件」、没有「全部隐藏固定件」；
  42 个 chip 里 20 个是固定件，默认全占位。
- 轴：`overlay.ts` 的角落三轴是**投影绘制**（随相机转，这点没问题），但它是
  **只读的 SVG**：不能点 X/Y/Z 转正视角，没有正交/透视切换，没有上轴切换。
  用户原话「xyz 轴要能够转化，现在这个轴是固定的，不好」——理解为「轴只能看不能操作」。
  （若用户指的是别的，先按 2.2 的 A 做，再校正。）

### 2.2 建议做法

| 项 | 做法 | 可证伪出口 |
|---|---|---|
| 图例收纳 | 默认收成一行：`零件 42 · 运动 22 · 固定 20` + 「展开」；展开后限高 2 排、可滚动、带搜索；「只看运动件」默认开 | 42 件回放的视口高度占比 ≥ 基线 +20%；`sandbox` DOM 断言图例高度 ≤ 2 排 |
| 轴操作 | 三轴可点：+X/−X/+Y/−Y/+Z/−Z 吸附正视角；`Home` 复原；正交/透视切换；双击轴回到等轴测 | `accept-viewport-orbit` 扩：点击 +Z 后相机 `up`/position 在容差内；截图对照 |
| 零件查找 | 图例搜索框（按名字过滤）+ 高亮；与 X14 的「视口点选」解耦（先做列表侧） | 输入 `spool` 后 chip 数 = 8，视口其余件不变 |
| 其它 | 「等等」按一次 UI 走查补齐：大装配首帧、悬停/选中、爆炸/半透明、100+ 件性能 | 走查清单逐条截图 + 通过/不通过 |

> X14（视口内点选）仍保持延后；本项只做「列表侧查找 + 图例收纳 + 轴吸附」，不依赖点选。

## 3. 大型项目：是 LLM 层还是插件层？先把「规划为空」量化

### 3.1 语料（冰雪城堡绕线器，已完成交付）

| 指标 | 数 |
|---|---|
| 零件种数 / 实例 / 接口 | 20 / 43 / 70 |
| 版本数 | 76（平均 3.8 版/种；曲柄 13 版、主轴 6 版） |
| 运行数 | 86：pass 29 / check 24 / fail 33（**66% 非 pass**） |
| 运行类型 | printability 52、motion 22、assembly-check 12 |
| 最终审计 | 运动/装配/契约/版本全绿；3 处已知锐边（打印融合/打磨） |

### 3.2 「总体规划几乎为空」具体空在哪

- `PROMPT.md` = 需求 + 已确认取舍 + 代决默认；`README.md` = 交付说明；
  `assembly.json` = 几何/接口契约；`cad_deliver plan` = **检查计划**（158 行），
  不是**设计计划**。
- 没有一张「需求 → 零件 → 接口 → 验证」的矩阵，也没有阶段门（概念/BOM/接口冻结/
  首次运动/打印性/交付）。于是每次需求变化（主轴 Ø10→Ø14、曲柄 D 榫 Ø10→Ø12）
  都是**事后级联**：改一个件 → 运动跑失败 → 发现漏改 3 个孔 → 再改。
  r074 的三个轴向干涉就是这么抓到的，不是计划出来的。
- 插件层确实缺一个**项目级 plan 工件**：现有工具面是「单件/单检查」，
  `affected` 只在版本变更后告诉你该重跑什么，不告诉你「还差哪些件、哪些接口没定」。

### 3.3 两个假设 + 判别实验

- **H-LLM**：模型没有先写计划，局部修复、上下文漂移。
- **H-插件**：工具面没有承载计划的工件与门，模型只能即兴。

判别实验（不靠感觉）：
1. 同一需求、新会话，强制先产出「需求→零件→接口→验证」计划并由人确认，再开工；
2. 记录每个需求的**返工轮数、触及零件数、首次运动 pass 前的版本数**；
3. 对照本次语料（无计划）的同一组数。

若计划组显著下降（目标：版本数 −30%、漏孔级联 0 次），说明主因在**规划缺失**
（插件该提供工件与门）；若仍高，说明 LLM 层执行/上下文问题，需要拆任务与检查点。

### 3.4 长期路线（不在 0.1.2 做）

- P0：`cad_plan`（或 `project.json` 的 plan 段）最小 schema：需求条目、零件表、
  接口表、验证矩阵、阶段门；只读 + 人确认，不自动生成几何。
- P1：阶段门接入 `deliver audit`：接口未冻结/验证矩阵有空行 → 不允许进交付审计。
- P2：用 2–3 个真实大项目回放标定「版本预算/返工率」，再决定是否做自动计划生成。

> 明确不做：让 LLM 一次生成完整 BOM 并直接开跑；计划必须可被人改、可被证据推翻。
