## 0.5 甄别规则：谁对？（2026-10-23 用户补充）

冲突不都是"代码错了"。判断顺序固定为：

| 层级 | 文档 | 冲突时 |

**DESIGN ↔ 代码冲突怎么判性质**（这是本条要求"注意甄别"的落点）：

### A1 `[实测]` 四个交付工具的输出契约在运行时边界上是坏的 — ✅ 已修（2026-10-23）

**现象**

`ToolRuntime.createSuccessResult`（`node_modules/@deepseek-ai/dsh-tools/lib/index.js:3415-3418`）
用编译后的 `output.schema` 校验返回值，不符即抛 `ToolOutputError`。用真实
`validateJsonSchemaValue` 校验真实编译 schema × 实现返回值：

```
validate_assembly  → missing required property "value.judgement"
                     missing required property "value.judgedBy"
check_assembly     → "value.judgement" is not a declared property (additionalProperties: false)
                     "value.judgedBy"  is not a declared property (additionalProperties: false)
preflight          → "value.timings"   is not a declared property (additionalProperties: false)
check_printability → missing required property "value.profiles[0].timings"   ← 修复时新发现
```

**根因**：`0849989` 的两个 hunk 落错对象——schema 加到了 `validate_assembly`
（`src/host/tools.ts:1650-1651`），返回值加到了 `check_assembly`（`:5336-5341`）；
`preflight` 的 `timings` 落进了 `check_printability.profiles[].properties`
（`:3727`，实测编译后位于 `properties.profiles.items.properties`）。

**影响**：这四个工具在真实调用路径上会抛 `ToolOutputError`（`check_printability` 在
profile 非空时——即默认 judge 模式——同样中招）。

**已修（2026-10-23）**：三处 schema 归位；`validate_assembly` 补上由报告派生的
`judgement`/`judgedBy`（干涉/过紧/不水密 → excluded）；并把校验**下沉到注册层**
（`src/host/tool-contract.ts` 的 `withOutputContract`），于是任何调用者——包括全部
`accept-*.mjs`——都过一遍与运行时同一份 schema。验收：`scripts/accept-tool-output.mjs`。

**改法**

1. `validate_assembly`：删掉误加的两行 schema（它确实没有 judgement；
   若要给，按 A3 的规则新增实际值）。
2. `check_assembly`：在它的 `output.schema.properties` 里补
   `judgement` / `judgedBy`（与返回值一致）。
3. `preflight`：把 `timings` 移进它自己的 schema，并把
   `check_printability.profiles[].items` 里那行误加的删掉。

**验收**：`node scripts/accept-tool-output.mjs`（随 A3 新建）对三个工具全绿；
沙盒各调一次真实工具，不再出现 `ToolOutputError`。

**状态**：☐

### A4 `[实测]` 参数报错 lint 已经空过 — ✅ 已修（2026-10-23）

**现象**

```
$ node scripts/audit-arg-errors.mjs
checked 0 negative argument guard(s); 0 do not name the offending field
```

`audit-arg-errors.mjs:37` 只匹配 `throw new Error(`，而 `0c31f3d` 把 9 处参数守卫
改成了 `throw argError(...)`（`tools.ts:962/1029/1286/1289/1693/...`）。
于是扫描对象变成 0，`accept-tool-contracts.mjs` 仍 PASS。

**改法**

1. lint 同时认 `throw new Error(` 与 `throw argError(`；`argError` 的调用签名是
   `(tool, field, problem, accepts, opts?)`，所以字段名可以**精确**取第二个参数，
   比原来的正则更可靠。
2. 加**阳性对照**：脚本自己注入一条不含字段名的坏守卫，必须被报出；
   报不出就 FAIL（照 `accept-thick-drag` 那条「同一 drag 在标注模式仍能标注」的做法）。

**验收**：`checked` ≥ 9；注入坏守卫时 `offenders` ≥ 1 且退出码非 0。

**已做**：lint 改为状态机解析 `argError` 的四个字符串参数（引号/括号/跨行都安全），
并加**内置阳性对照**（4 个站点、2 个应报错，报不出即退出 1）。
修的时候发现**第二层缺陷**：旧实现把 `msg` 取成「包含守卫那一行」，
而守卫里就有字段名，所以**任何同行守卫都不可能被判为漏写**——断言在最关键的形状上恒真。
现在只搜索 `throw new Error(` 之后的文本。结果：9 个站点全绿，`checked 0` 不再可能。

**状态**：☐
