# 方向性决策记录（append-only）

## 2026-10-03：版本管理采用 git（本地仓库起步）

**要解决的问题：** 项目完全没有版本管理，导致（a）无法回答"哪次改动引入了问题"；
（b）上一轮交付未经沙盒验证的改动没有快照可比对；（c）dsh 升级覆盖宿主 patch 后
无法追溯当时改了什么。

**决策内容：** 在项目根目录 `git init`，本地仓库起步，暂不设远程。忽略规则见
根目录 `.gitignore`：依赖（node_modules）、构建产物（dsh-cad-harness/lib）、
第三方大文件（bin/OpenSCAD AppImage、lib/BOSL2）、生成工件
（examples/*/out、data/versions、沙盒截图）全部不入库；语料文本
（scad/datums/manifest/验收基线 shots）入库。

**理由：** 项目全部是文本（TS/MD/YAML/SCAD），git 的 diff/回滚正好覆盖本次
事故的核心需求——"每次交付有快照、每次验证有输出可对"。不需要远程即可获得
全部收益；后续需要备份/协作时再推私有远端，不影响现有结构。备选的
"目录快照脚本"无 diff 能力、"SVN"无本地分支优势，均放弃。

**依据：** 2026-10-03 沙盒复核事故（DESGIGN §15）：四处已交付改动与现实偏差，
逐一排查时没有任何基线可比。初始快照 289 文件 / 13MB，无大文件泄漏。

**影响：** 后续每次插件改动按 AGENTS.md 工作流提交（执行摘要 + commit）；
dsh 升级后跑 `accept-image-budget.mjs` 并以 commit 记录结果；宿主 patch
（若重新引入）必须在 DECISION-LOG 登记并配升级后重放钩子。

## 2026-10-03：用户图裁剪豁免采用插件内执行器方案（方案 B）

**触发条件：** 第 1 条（用户拍板："做B"）。

**要解决的问题：** 现货 dsh 的 `dsh-compaction-image-offload` 最老优先裁剪、无用户图
豁免，用户参考图必然第一个出局。方案 A（召回工具）已交付但依赖模型主动调用；
需要"被动侧"的保护。

**决策内容：** 不打宿主 vendor patch。用本插件的 bundle patch 将现货
`image-offload` 行 `disable: true`，由插件自身监听 `IMAGE_OFFLOAD_REQUIRED`
（`agent/request-error` / `compaction/summary-error`）并以同样的
`image/offload` 会话决策事件执行"跳过 user 消息顶层图片"的最老优先裁剪。

**理由：** 全部代码在本仓库，dsh 升级免疫且可沙盒验证；现货执行器实现可读，
移植保真度高。对比 vendor patch（升级即失效、沙盒只读无法重放）与召回工具
（被动侧无保护），这是唯一同时满足"升级安全 + 被动保护 + 可验证"的路径。

**依据：** 现货执行器全文已通读（dsh-compaction-image-offload lib/index.js，
0.2.0-rc.2）；其接缝为 `sessions.registerMessageProjection` +
`agent/request-error` / `compaction/summary-error` 事件；DESGIGN §15.1 第 4 条
实测记录。

**影响：** 插件承担 offload 职责，接缝形状随 dsh 演化需跟进（验收脚本盯住）；
现货行被 disable 后，非 CAD 路由也走本插件的执行器——行为差异仅"用户图豁免"。

## 2026-10-03：图片预算改为会话级窗口（方案 B′，用户拍板）

**触发条件：** 第 1 条（用户拍板："这个B′才是我想要的"）。

**要解决的问题：** 图片预算（deepseek 24 张 / pi-ai 256KiB）是路由级全局配置，
对标准模式不公平（256KiB 对真实截图≈2-5 张就开始裁）；而"仅造物模式限图"
无法在适配器接缝上直接表达。方案 B（动态翻全局旋钮）被否决：并发会话下
全局旋钮互踩，正确性只在单会话前提成立。

**决策内容：** 适配器预算放宽为兜底值（pi-ai 8MiB，仅防超大附件；deepseek
24 张对聊天无感，保留）。插件在 `llm/stream` 观察点（`options.sessionId` →
`ctx.sessions.get()` → `session.header.agentPreset`）对造物模式会话执行
**24 张保留窗口**：超窗即主动记 `image/offload` 决策，下一请求合规。
标准模式不主动限图。

**理由：** 每会话独立判断，无全局旋钮竞态；标准模式完全不限图；执行器与
选择函数已存在（方案 B），复用度高。代价：预算收紧后第一个请求仍超窗
（多付一次视觉 token），之后合规——验收和文档已注明。

**依据：** `llm/stream` options 携带 `sessionId`（dsh-llm types L524，
agent-loop buildRequest 盖章）；`session.header.agentPreset` 为创建事实
（dsh-session L1052/1708）；`ctx.sessions.get(sessionId)` 存在
（dsh-session L1628）。

**影响：** pi-ai 兜底预算变化需同步 accept-image-budget 期望；窗口逻辑依赖
`llm/stream` + sessions 查询接缝，dsh 升级漂移由验收脚本盯住。

## 2026-10-03：标准模式回归 dsh 出厂默认，图片干预仅限造物模式

**触发条件：** 第 1 条（用户拍板："标准模式不改变dsh的默认配置"）。

**要解决的问题：** §16.4 落地后仍有两处全局干预（deepseek 24 张 patch、pi-ai
8MiB settings 写入），标准模式被插件改了行为；且"永不裁剪"本身也不是 dsh 默认。

**决策内容：** 撤销全部路由级预算（llm-deepseek patch 删除、pi-ai settings 写入
删除）；offload 执行器按 preset 分派——cad 会话 = 24 张窗口 + 用户图豁免，
其余 preset = 与现货执行器逐字节一致（最老优先、无豁免）；投影层允许用户图
决策重放（非 cad 现货决策必须可回放）。

**理由：** 用户模式/非用户模式界限清晰：插件只在用户点名的造物模式里改变行为，
标准会话与裸 dsh 无差别。执行器已持有接缝，分派零边际成本。

**依据：** accept-image-offload 同夹具对照（standard 选择与现货逐字节一致）；
accept-image-budget 组合树确认 llm-deepseek UNPATCHED；三套验收全绿。

**影响：** 造物会话预算完全依赖主动窗口（超窗首请求多付一次）；非 cad 会话若
用户自行配置路由预算，得到现货处置（含用户图被裁——那是 dsh 默认）。

## 2026-10-05：评测基准落在 `examples/bench/`，五道题，顺序按"综合度"而非"单项难度"

**触发条件：** 第 1 条（用户拍板："从易到难给一套……也是今后测评插件优化后能力
是否提升和那个 LLM 配合本插件最佳的指标"）。

**要解决的问题：** 现有 `examples/` 的五份显微镜示例都带大量主观判断（"像不像
参考图""仿真顺不顺"），既无法回答"插件改完到底变强没有"，也无法横向比较不同
LLM 与本插件的配合度。缺少一份起点固定、判据机检、可重复的题库。

**决策内容：** 在 `examples/bench/` 下建五道题并各自自包含（固定题面
`prompt.md` + 机检判据 `rubric.json` + 人工答案 `key.md`，参考图与语料同目录）：

| 编号 | 题目 | 同时压测的能力车道数 |
|---|---|---|
| `00-smoke` | 工具链冒烟自检（不是难度级，是仪器校准） | 全工具各一次 |
| `01-mortise-bench` | 榫卯木长凳 | 1（L0） |
| `01b-diagnosis` | 诊断已交付语料 | 审计/证据链 |
| `02-steam-engine` | 往复式蒸汽机 | 3（L1 运动 + L1 刚体 + L2 流体） |
| `03-microscope` | 单目复式显微镜 | 6（+ 可打印性 + 外观还原 + 长程记忆） |

**理由：** "从易到难"有两种读法。按单项能力难度排会把显微镜放在中间，但显微镜
的车道数（6）高于蒸汽机（3），阶梯随即非单调——只要某个模型在蒸汽机上的得分
高于显微镜，"极限在哪"这个问题就自相矛盾了。改为按同时压测的车道数排序，阶梯
单调，且用户自己也认定 microscope5 就是当前上限，上限项本就应该压在最后。

**依据：** 插件现有 18 个 CAD 工具（非 PROJECT.md 所写的 11 个）；microscope5 语料
实测：26 条接口中 `motion-clearance` 为 0，而其中 6 条 `type` 写着转动副/滑动副；
全部 run 里只有 r046、r048 覆盖了全部 16 件，两次都是 `fail`。

**影响：** 后续插件改动以本题库的分数变化作为"是否提升"的判据；`examples/`
下既有的五份 microscope 语料保留为历史语料，不再作为评测基线。

## 2026-10-05：长凳示例定为木质，不纳入可打印性车道

**触发条件：** 第 1 条（用户拍板："木质哈，提示词里面已经要求了"）。

**要解决的问题：** 若把长凳当打印件，可打印性判据会与木工配合语义（顺纹/横纹
胀缩）混在一起，两套知识各占一半分数，谁也说不清是能力不足还是知识不同源。

**决策内容：** 第 1 题明确为木工件，材料写作"木材"，**不调用
`check_printability`**。该题只考四件事：L0 几何与 datum、榫卯配合的可执行契约、
多实例与子装配、阴性对照。可打印性车道交由第 2、3 题承担。

**理由：** 收窄单题车道反而让"易"成立，也让失败可归因；木工语义只能推理不能
仿真（插件无材料各向异性），因此单独作为人工判据项，不混入机检分。

**依据：** manifest 子件本就带 `material` 字段，写入语义无额外成本；用户题面
已含"木质"。

**影响：** `rubric.json` 的 `features` 中出现一组"只能在 `key.md` 里人工判"的
条目，runner 需支持 `manual` 类型的得分项。

## 2026-10-05：显微镜示例的外观以参考图为准，内部光学自由

**触发条件：** 第 1 条（用户拍板："以图为准：外轮廓服从图，内部光学自由"）。

**要解决的问题：** microscope5 的 PROJECT.md 用 M12 板机镜头 + 双端口 + LED 照明
座定死了内部光学，而这些规格决定了外轮廓（筒长、筒径、台下结构），与参考照片
（标准 160mm 筒长 + 转换器 + 台下聚光镜）是**两台不同的机器**。题面里那句"图片
与 PROJECT.md 冲突处以 PROJECT.md 为准"让"照图还原"变成了不可能任务，随后又被
当成能力短板记录——这是规格冲突，不是能力缺陷。

**决策内容：** 外观类判据一律以参考图为准：筒长/筒径/臂形/底座形从图推；内部
光学（是否用 M12 板机镜头、单端口还是双端口、LED 还是聚光镜）由 Agent 自定，
不计入外观分。参考图同时附一张"还原/不还原"清单，转换器与台下聚光镜列入
"不还原"。

**理由：** 让两件事解耦，外观分才指向"形状还原能力"，而不是"是否服从了某个
与照片矛盾的光学方案"。

**依据：** microscope5 交付摘要第 1 条偏差自述（单物镜、无转换器，属用户指令）；
参考图分析见下一条。

**影响：** 第 3 题的 `key.md` 需同时给出"图中量得的轮廓数值"与"内部光学可自由"
的说明；外观判据不得引用 PROJECT.md 的 156/13.0 那套光学数。

## 2026-10-05：参考图采用 AI 去转换器后的新图，必须先净化并剔除 band4

**触发条件：** 第 1 条（用户拍板："我用 ai 去掉了转换器了……能否使用？"）与第 2 条
（本节数据）。

**要解决的问题：** 手头两张参考图各有缺陷：microscope5 会话里那张（800²）带物镜
转换器，与"不做转换器"的题面冲突；用户新给的 1024² 图已去掉转换器，但右下角带
第三方 AI 工具水印（"千问"），且分辨率变化后判据是否仍可比需要验证。

**决策内容：** 采用新图。归档前做两步处理：(1) 裁切掉右下角水印（水印散点
x≥943、y≥950，主体包围盒 x[307,716] y[129,895]，按 x 方向裁切即完全排除）；
(2) 外观判据的十段归一化宽度剖面中**剔除 band4（40%–50% 高度段）**，改为独立
的"旋钮 Ø 与高度位置"特征项。

**理由：** 两张图的十段剖面里有九段差值 ≤0.004，只有 band4 差 0.112，而 band4
正是转换器所在高度带。既然题面明确不还原转换器，用 band4 计分等于罚模型去做
我们禁止它做的事。水印必须去掉是因为它会把主体包围盒撑到 y=990，使 H/W 从
1.871 错成 1.260。

**依据：** 两图同法轮廓分析（最大连通域法）：原图 320×600、H/W=1.875；新图
410×767、H/W=1.871；剖面差 `[.004, 0, -.004, .001, .112, -.002, -.002, 0, -.003, -.001]`。

**影响：** `03-microscope/参考图.png` 为净化后的归档件；`landmarks.json` 记录
从该图量得的九段剖面与比例，band4 标注为 `excluded: turret-removed`。

## 2026-10-05：修 BOSL2 接线缺陷，并与三条历史故障一起固化为回归钉子

**触发条件：** 第 3 条（经严格数据分析的决策：实测复现 + 历史故障记录交叉验证）。

**要解决的问题：** `src/host/compile.ts` 把 `OPENSCADPATH` 设成了
`<pluginRoot>/../lib/BOSL2`，而工具描述与 `cad-toolbox` skill 都要求模型写
`include <BOSL2/std.scad>`；后者会被解析成 `lib/BOSL2/BOSL2/std.scad`，**所有
BOSL2 include 全部失败**，且失败是静默的（OpenSCAD 只给 WARNING，顶层对象为空，
编译仍报"成功"）。microscope5 交付摘要第 7 条"BOSL2 在编译环境不可用：齿轮为
手写渐开线（弧段法），螺纹为 rotate_extrude 弧段法"正是这个缺陷的现场记录——
一次插件接线 bug 被记成了模型的短板。

**决策内容：** `OPENSCADPATH` 改为指向**包含 `BOSL2/` 的那一层**，同时兼容打包
（`<plugin>/../lib`）与直跑源码（`<plugin>/src/../../lib`）两种 `pluginRoot`
语义，并把 `lib/BOSL2` 自身也加入搜索路径，使裸 `include <std.scad>` 同样可用。
回归覆盖按"已在别处钉住的引用之、缺口才新写"处理：

| 历史故障 | 覆盖 |
|---|---|
| BOSL2 include 静默失败 | **新增** `scripts/accept-bosl2.mjs`（14 项断言，含路径形状、齿轮外径 = mod×(teeth+2)、M6 螺钉、裸 include 拼写） |
| `simulate_motion` pivot 重基 | **新增** `scripts/accept-motion-pivot.mjs`（原先**无任何覆盖**；断言默认 pivot 取自关节锚点、回退几何中心、显式 pivot 覆盖、且 run 里存的 STL 真被平移到位） |
| 齿条按 `pitchRadiusMm` 严格比 | 已由 `scripts/accept-p2.mjs` 覆盖，不重复 |
| `validate_assembly` 的 `pose` 绕 datum 轴 | 已由 `scripts/accept-p3.mjs` 覆盖，不重复 |

**理由：** 这类"工具坏了、模型背锅"的缺陷会让整个评测失去意义，必须在跑基线之前
修掉并自动化守住。已覆盖的故障不重写测试，避免同一断言两处维护。

**依据：** 实测：`OPENSCADPATH=…/lib/BOSL2` → `WARNING: Can't open include file
'BOSL2/std.scad'`、无 STL；修复后 `spur_gear(mod=1,teeth=20)` 实测外径 21.99mm、
面宽 6.00mm，`screw("M6",length=20)` 轴向 20.00mm，两脚本分别 14/14 与 12/12 全绿。

5→937mm³"与"validate_assembly 的 pose 绕世界原点、零件被甩出 176mm"；pivot 修复路径

## 2026-10-05：手册是 SUT 的一部分，不是污染源；基准冻结为 v0，新增 S 列

> **本条取代同日"01b 改为两臂对照实验"条中的**：①两臂的定义（由"有/无手册"
> 改为"手册版本 A / 手册版本 B"）；②01b 跑标准模式（改回**与其余各题一致的
> 造物模式**）；③"把手册当泄漏去遮"的全部表述。其余（`g-grader-access` 检测、
> 目录分离、delta 记录）不变。

**触发条件：** 第 1 条（用户拍板："把 skill 当做污染？我觉得不合适……应该对比的是

将评测目标改为 skill 能否正确生效，而不是改 skill。以后本版本就是基准"）。

**要解决的问题：** 上一条的设计里，01b 的一臂是"无手册"，并被表述为"把泄漏变成
自变量"。**这个框架从根上错了**：它把 `cad-toolbox` skill 当成了要消除的噪声，
而 skill 正是本插件要发布的产品的一部分。插件的价值主张之一就是让手册把踩过的坑
带到下一轮——所以"手册提前写了结论"不是缺陷，"手册能不能让模型做对"才是被测目标。

按旧框架做下去会得出一个自相矛盾的结论：测出来的分数越高，越说不清是模型强
还是手册写得好；而一个"藏掉手册"的分数，回答的是"模型自己行不行"，
不是"这个插件行不行"——但后者才是我们要的。

**决策内容：**

1. **被测系统（SUT）定义为 `dsh-cad-harness`（含 `cad-toolbox` skill 与工具描述）
   × 模型**，并随 git commit 冻结；`SKILL.md` 另记 sha256。
   **基准 v0 = commit `76b6661f` + SKILL.md
   `8e2717f9694e6a1d5a5a18e26ced68fa9972f4e25304bcde476266618bc44da3`（313 行）**，
   本变更集提交后生效。以后每次改 `SKILL.md` 都拿它当对照。
2. **边界规则**取代"污染"表述：**属于 SUT 的不算泄漏；SUT 之外的答案来源才算。**
   skill / 工具描述 / 预设 → 不算；`graders/` 的判据与答案、`docs/DECISION-LOG.md`、
   `examples/microscope5/**` → 算，靠目录分离 + `g-grader-access` 检测。
3. **所有 LLM 题统一在造物模式跑**，用同一个 SUT；手册出不出现在上下文里由 SUT 的
   加载逻辑决定，**不人为干预**。
4. **新增 `S` 列（skill 生效度）**：`rubric.json` 里标 `inSkill: true` 的条目，
   模型做到了几件；另记 `S0`（skill 是否被加载，`false` 时 `S` 记 `N/A`）。
   `S` 与 `P` 有意分开——手册要求跑整机验证而模型没跑但结果碰巧对，就是 `P` 高
   `S` 低。**"改 skill 后生效度有没有上升"由此才可测**，这正是用户要的评测目标。
5. **01b 的对照改为 skill 版本 A/B**：两臂靠**换 `SKILL.md` 文件**区分（同模型、

**理由：** 用户的两点判断都成立：①把手册当污染会测错对象；②若真在意"手册写了答案"，

**依据：** 分类标注时实测：`SKILL.md` 中 "negative control"/"阴性" 出现 **0** 次，

**影响：**

## 2026-10-08：仿真定位为"水电路"级基础设施，但不得垄断、不得阻拦自建

**触发条件：** 第 1 条（用户拍板）。用户原话："从设计层面必须明确，仿真模拟是水电路
级别的基础设施，但是我们不阻止 LLM 自己搭建水电路，意味着我们应当尽可能的在一般
情况下提供可复用的工具，但是绝不阻拦 LLM 根据实际自行拉电网。"

**要解决的问题：** 仿真能力该按什么定位来设计。此前 `simulate_fluid` 的问题
（`M4-M5-REVIEW.md`）暴露出一类风险：工具语义不清时，LLM 会拿它去回答它表达不了的
问题，并产出一个**语义不明的可信数字**。

**决策内容：**

1. **定位为基础设施**——把通用、可复用、可复算的部分做到位（稳定接口、明确语义、
   内置验收、可信默认值）。
2. **但绝不垄断**——LLM 可以用脚本/bash/node/python 自建求解器与分析流程。工具不是
   唯一通道。
3. **硬推论**：既然允许自建，工具的价值主张只能是**更省、更可信、可复算**，不能是
   "唯一许可"。由此强制六条设计要求（工具声明能力边界 / 报告回显实际算什么 /
   验收判据内置 / 自建产物可登记可验收 / 预制的是工况模板而非方法 / 不设读写障碍）。
4. **模板形态定为"诊断 + 处方 + 复验"**，而不是"再包一层求解器"。样板是用户举的
   "哪里容易断裂就加加强筋"：诊断（找高应力）→ 处方（加筋/圆角/加厚）→ 复验（对比）。

**理由：** 两条原则同时成立时，唯一自洽的竞争方式是"可验证性"。若工具试图通过垄断
来保证正确性，就会与原则 2 冲突；若允许自建却不提供可比性，则自建产物无法评估，
基础设施也就失去意义。

**依据：** `DESGIGN.md §25`（含六条设计要求、模板判据、候选模板清单、接口形状）。
实证来源：`experiments/20261008_simulate_fluid_thick_wall_sign_bug.md`（工具语义不清
导致的可信错数）、`M4-M5-REVIEW.md`（工况表达缺失）、以及首轮基线的模型行为证据
（不会主动做可信性判断、列数据不下结论）。

**影响：**

  验收通道**。

   **保留已实现部分不删，但降级为后期项，不再作为主线。**
2. **语料必须记 provenance。** 每条仿真结果标明是预制工具还是 LLM 自建脚本产生的，
   以及所用假设。
3. **`<cwd>/sim/` 为自建仿真工作区**，工具与文档承认它是合法落点。
4. **首条模板线选「承力与加强」**，但**先检查现有引擎能否承担**。

**理由：**

- MPM 的设定量最多（物性、声速/CFL、网格无关性），而我们连流体身份都没有——把最难
  的事放在基础设施最薄弱处。用户对此定性为判断失误，责任在己，要求明确承认。
- 允许自建（前一条决策）却不在语料里区分来源，则**无法判断坏结果该归谁**，
  基础设施的价值也无从度量。
- 不设读写障碍的落地需要一个明确的自建落点（沙箱写权限限于工作区）。
- 「承力与加强」通用度最高且设定量最少，是最合适的打样对象；但**必须先验证引擎**，
  避免又一次"在不具备的地方做最难的事"。

**依据（第 4 条的检查结论，2026-10-08）：**

| 引擎 | 能做静力应力吗 | 证据 |
|---|---|---|
| Manifold（几何） | ❌ 无物理 | 只做布尔/体积/干涉 |
| rapier（刚体） | ❌ 刚体按定义无内部应力 | `physics.ts` 只输出 `settledPenetration`/`toppleNoted` |
| MPM | ❌ 纯流体、无 F 路径 | `grep "deformationGradient|elastic|plastic|shearModulus" src/host/mpm.ts` → 空；`grep "FEM|youngModulus|poisson|vonMises" src/` → 空 |

**同时发现一条捷径**：`sdf.ts` 已产出**规则网格上的逐格体素化**
（`solidMask` + `solidNormal` + `cells/dxMm/originMm`），恰好是 hex8 线弹性 FEM
所需的网格——**绕开体网格剖分与稀疏矩阵组装**（规则模板 ⇒ matrix-free CG），
`solidNormal` 可直接施加表面载荷。代价是边界阶梯状、绝对精度有限，但**足以做
"加筋前后降了多少"的相对比较**——正是该模板要的输出。
⇒ 走**小体素 FEM 车道**，不要给 MPM 加固体路径（显式动态做静力是其最弱工况）。
第一条验证：**悬臂梁端部载荷 vs 梁理论**（`δ=FL³/3EI`、`σ=Mc/I`）。

**影响：**

- `M4-M5-REVIEW.md` 新增 §7（引擎检查 + 体素 FEM 路径）；`DESGIGN §25.6` 记路线图修订。
- MPM 相关的复核议程（§24 的工况表达与物性）**排到后期**。
- 后续所有仿真产物需带 provenance；自建产物落在 `<cwd>/sim/`。
- 新增 FEM 车道是**比修流体更大的决策**，本次只确认方向与前置检查，**尚未拍板实现**。

## 2026-10-08：插件自带 Python 运行时——宿主首次运行供给独立 CPython

**触发条件：** 第 1 条（用户拍板）；第 3 条（供给策略、落点与锁一旦落地，后续所有
Python 领域能力都挂在它上面，换路要重下重装）；第 4 条（波及 host 接线、工具目录、
分发方式、文档与验收）。

**要解决的问题：** 插件要给别人用，而"别人机器上一定有可用的 Python"不成立——
发行版 Python 从 3.8 到 3.14 都有、PEP 668 禁止直接装包、conda/pyenv 各说各话。
用户原话："不仅仅要加，而且要能够别人安装插件的时候也能够自动安装一个 python
运行时；Windows 下应该好解决，用一个嵌入式的 python 运行时即可，但是 Linux 下
应该怎么解决……关键是优雅的解决。"同时要回答：放在哪个时机、走哪条路径。

**决策内容：**

1. **供给方式 = 宿主自行供给独立 CPython。** 从 python-build-standalone 取
   `install_only_stripped` 归档（pin `3.13.16+20261003`），校验 sha256 后解包，
   再用它建 venv、按带 hash 的锁装依赖。**不做 npm postinstall。**
2. **时机 = 运行期而非安装期。** 默认 `auto`：启动只做健康检查，**首次调用阻塞供给**
   （带进度）；`eager` 才在启动时后台预热（不阻塞激活）；`python_runtime` 工具可显式
   provision/repair/status。
3. **来源优先级：** ① DSH 载体自带的 primary runtime（`DSH_PRIMARY_RUNTIME` /
   `DSH_BUNDLED_PRIMARY_RUNTIME`，有就直接用它建 venv，省一次下载）→ ② 自供给
   pbs 运行时 → ③ 显式 opt-in 的系统 python。
4. **Windows 不用官方 embeddable。** 它没有 `venv`/`ensurepip`，`python._pth` 默认关
   site，装依赖要自己补 pip/改 `._pth`；pbs 的 windows `install_only` 与 Linux/macOS
   是同一类产物（自带 pip + venv）。**"五平台一条代码路径"优先于省那 15MB。**
5. **依赖集 v1** = `numpy` `scipy` `trimesh` `manifold3d` `networkx` + `rapier3d 0.36`
   （HARNESS §12.4 的数值/网格档 + 物理交叉验证档）；OCP/build123d 仍后置。
   **同日补充**：把 `scikit-fem 12.0.2` 也钉进锁——本仓库已有
   `scripts/xval-cantilever-scikitfem.py`（同日 scikit-fem 交叉验证提交 256674a），
   而"跑不了仓库里已有 Python 工作"的运行时不算交付；它是纯 Python wheel、
   只依赖 numpy+scipy，不增加平台矩阵与编译负担。
6. **落点** `$DSH_HOME/cad/runtime/`（跨项目共享，与 `telemetry/` 同级）：
   `python/<版本>/` 解释器、`venv/` 依赖、`runtime.lock.json` 与 `requirements.lock`
   锁、`state.json` 状态。
7. **工具面 v1** = `run_python`（内联/脚本、超时、完整 traceback）+ `python_runtime`
   （状态/修复）。领域 worker 的 JSON-lines 协议（HARNESS §12.3）随后长在同一接线点上。
8. **网络可配**：`DSH_CAD_PYTHON_MIRROR`（解释器镜像）、`DSH_CAD_PYTHON_INDEX_URL`
   （pip 索引），官方源 + 国内镜像兜底；`DSH_CAD_PYTHON=off` 关闭自动供给。
9. **rapier3d 的平台规则（用户拍板，2026-10-08 同日）**：darwin-x64 没有 wheel，
   **该平台物理继续用 TS 引擎**（`rapier3d-compat` 的 canonical 地位不变），Python 侧
   不装它；而且**这一条必须在安装期确认并明说**——锁里的
   `# cad-exclude: darwin-x64 | <原因>` 负责裁剪，`state.json.skipped` 记录，
   `python_runtime` 报出原因。理由：静默缺包会被读成"库坏了"，而真相是"平台差异 +
   物理留在 TS"。

**理由：**

- postinstall 方案不成立：pnpm 11 拦依赖脚本，`installBundle` 会失败并把待批脚本交给
  用户在插件页批准重试，失败/取消还要回滚 `package.json` 与 `pnpm-lock.yaml`

- 不把二进制塞进 npm（平台包方案）是**先不做而非不做**：每平台 ~35MB、升一次 Python

- 借用 DSH 载体自带的 Python 是零成本快路径，但它只带 Office 那套库

**依据（2026-10-08 实测，本机 Arch Linux / Node 26.10.0 / uv 0.12.22）：**

| 验证项 | 结果 |
|---|---|
| pbs 供给 | `uv python install 3.13` → `cpython-3.13.16-linux-x86_64-gnu`，33.4MiB 压缩 / 105MB 展开 / **3.5s**，自带 pip 26.2.1 + `venv` |
| 免编译器 | venv 内装 numpy/scipy/trimesh/manifold3d/networkx：全部命中预编译 wheel（`cp313-cp313-manylinux_2_27_x86_64`、`py3-none-any`） |

| rapier3d wheel | 0.36.1 有 macos-arm64、manylinux x86_64/aarch64、musllinux x86_64/aarch64、win_amd64（`cp39-abi3`，3.13 可用，~5–6MB）；**无 darwin-x64 wheel** → Intel Mac 上不装 rapier3d |

**影响：**

## 2026-10-08：判据修正——对 LLM，Python 是第一语言；能迁的默认迁 Python

**触发条件：** 第 1 条（用户拍板）；第 4 条（决定后续所有工具的归属、批次与验收方式）。

**要解决的问题：** 同一天先落地的运行时决策只解决了"有没有 Python"，没解决"**哪些工具
该用 Python**"。我在 `docs/TOOL-RUNTIME-MATRIX.md` v1 里用**性能/精度**当判据，把大多数
工具判成"保留 TS"。用户指出这是判据错误，并且承认自己在先前决策里**没有把依据说清楚**：

> "多数 llm 对 python 明显有更强的编码能力，部分库有更新的版本，在部分领域明显有更好
> 生态等等原因，所以我坚持对 llm，python 是第一语言。"
> "能迁移到 python 的应当优先迁移到 python，只有明确负收益的才不做。"

**决策内容：**

1. **判据**：**领域逻辑默认迁 Python**。保留 TS 只有三类理由，每条都要写出来：
   ① **平台接线**（DSH 规定的宿主面：cordis 生命周期、`ctx.tools.register`、
   `ctx.attachments`、`connection.fetch` 路由、面板/回放、会话与项目路径解析、
   `llm/stream` 遥测）；② **明确负收益**（必须**用实测数据**证明，不许用直觉）；
   ③ **canonical 冲突**（同一问题域只能有一个权威实现，换边需重定基线）。
2. **Q1 = B：领域数据"文件即契约"。** `parts/versions/runs/assembly.json` 保持磁盘
   JSON + 固定 schema，两侧读写；TS 的 HTTP 路由直读文件。理由：面板保持零 IPC，
   迁移可以**逐工具**进行，不必一次性搬存储。
3. **Q2 = A：canonical 随迁 Python。** 物理的权威实现迁到 Python `rapier3d`，
   **darwin-x64 例外**（无 wheel，继续用 TS `rapier3d-compat`，已在前一条决策落地）。
   代价明确：TS 侧现有物理验收（17/17 + 24/24）**必须在 Python 侧重跑**才算数。
4. **前置条件**：**batch 0 = 常驻 worker + JSON-lines（HARNESS §12.3）**。它是"能迁就迁"
   的开关——见下方依据里的冷启动数据。
5. **"明确负收益"必须数据化**：本条目**不预先认定任何工具是负收益**；清单见
   `docs/TOOL-RUNTIME-MATRIX.md`，每一项都要有实测数字（冷启动/worker 往返、空间索引、
   路由 IPC、平台 API 可达性），测量结果落 `experiments/`。

**依据：**

**(a) LLM 与语言——证据盘点（含反向证据，不美化）：**

| 说法 | 证据 | 结论 |
|---|---|---|
| 评测与语料以 Python 为锚 | HumanEval / MBPP 是 Python 基准；MultiPL-E 的做法就是**把它们翻译**到 18 种语言（[arXiv:2208.08227](https://arxiv.org/abs/2208.08227) 摘要："can generate semantically correct **Python** code, little is known about their abilities with other languages"） | ✅ 支持"Python 是重心" |
| "多数 LLM 对 Python 明显更强" | **同一篇** MultiPL-E 的结论是 "Codex **matches or even exceeds** its performance on Python for several other languages" | ⚠️ **这条要打折**：至少对 Codex 一代的多语言基准，Python 不是绝对最强；不能拿它当普适结论 |
| 训练语料分布决定下游表现 | Magicoder 论文讨论语料分布与表现的关联（[ar5iv 2312.02120](https://ar5iv.labs.arxiv.org/html/2312.02120)） | ✅ 支持"语料重力在 Python" |
| 部分库版本更新 | manifold3d(PyPI) **3.5.4** vs npm manifold-3d **3.5.4**（同日核实，**同版本**）；`@dimforge/rapier3d-compat` 最新 **0.21.0** vs PyPI `rapier3d` **0.36.1**（版本号体系不同，不可直接比大小） | ⚠️ 对 manifold 不成立；rapier 的差异是**能力**不是版本 |
| 部分领域生态更好 | 可核实：`scikit-fem`（Python 独有，JS 侧只有杆系）、`build123d`/`cadquery-OCP`/`FreeCAD`（B-rep/STEP 的 Python 优先路线）、`mujoco`/`pybullet`；且 **`rapier3d` Python 绑定有 JS 绑定没有的软体 API**（HARNESS §12.4 实测） | ✅ 强支持 |

⇒ **判据成立的理由不是"Python pass@1 更高"这一条**（它不普适），而是：
**评测/语料重心 + 领域库生态 + 绑定能力 + LLM 写 Python 时的可读/可自建**。这条要在
文档里如实写成"生态与语料依据"，不要替用户把它说成"基准证明 Python 更强"。

**(b) 冷启动（本机实测，2026-10-08）：**

| 场景 | 实测 |
|---|---|
| 裸解释器 `python3 -c pass` | **11 ms** |
| `import numpy, scipy` | **~80 ms** |
| 再加 manifold3d / trimesh / scikit-fem | 估 0.1–0.3 s（待 batch 0 实测） |

⇒ 每次调用起新进程 = 给所有小工具加 0.1–0.3 s。这不是"某工具不该迁"的结论，
而是"**worker 必须先落地**"的结论（常驻进程把每次调用压到 IPC 量级）。

**影响：**

- `docs/TOOL-RUNTIME-MATRIX.md` 重写为 v2（判据换成"默认迁"）；"明确负收益"清单降级为
  **待测项**，每条都要有数字。
- 后续批次：batch 0（worker）→ batch 1（纯计算域：fluid/FEM/measure/check）→
  batch 2（生成/渲染/导入/合并的领域部分）→ batch 3（存储，按 Q1=B 保持文件契约）。
- 物理迁移（Q2=A）会换绑定版本，**必须重跑物理验收基线**；darwin-x64 永远走 TS。
- `HARNESS.md §12.1`（"TS 是平台接线层，Python 是领域运行时"）从原则变成**执行判据**：
  它此前只是记录，从未被用来裁决单个工具的归属。

**同日实测补充（2026-10-08，报告 `experiments/20261008_python_migration_measurements.md`）：**

| 我原先猜的"负收益" | 实测 | 判定 |

## 2026-10-08：阶段决定——现在只做 TS↔Python 实现对比；原生（C/C++/Rust）留中后期

**触发条件：** 第 1 条（用户拍板）；第 4 条（决定批次内容与顺序）。

**要解决的问题：** 我在测"哪些内核该迁 Python"时顺手做了原生 C 基准（MPM 内核比 TS 快
3.7–4.6×），用户指出这超前了。

**决策内容（用户原话要点）：**

1. **C/C++ 正在做的补完，还没做的就不要做了**——那件原生基准拿到数即止，不再开新的原生工作。
2. **"用 C/C++ 或 Rust 替代性能不够的 Python 代码"是中后期的事**，现在做太早。
3. **目前只对比 JS/TS 与 Python 实现的差异。**

**依据（同日实测，报告 `experiments/20261008_python_migration_measurements.md` 补充 2；
脚本 `dsh-cad-harness/scripts/measure-python-gains.mjs`）：**

| MPM 内核（每步） | 3.1 / 23.4 / 88.3 ms @ 8.8k/70.6k/262k 粒子 | 11.4–12.7 / 59–71 / 230–263 ms | **Python 慢 2.5–4×** |
| 体素 FEM（悬臂梁） | 0.1 / 1.7 / 27.8 s（总） | 组装 1.7 / 10.7 / 80.1 s + CG 0.04 / 1.2 / 4.9 s | **组装慢 3–17×**；CG 求解反而快 1.5–2.3× |
