# microscope3 建模过程 · 上下文 token 使用分析报告

数据日 2026-10-03 · 分析对象：`examples/microscope3/` 全程建模（M1–M4 + 收尾修复 + 第二日续作）

---

## 0. 数据来源与方法（先说口径，数字才可信）

- **来源**：`~/.dsh/cad/telemetry/usage.jsonl` —— 插件在每个 LLM 请求发出后写入的逐请求记录
  （模型、图片数、图片估算 token、文本估算 token），共 3247 行 profile 全量。
- **圈定**：按语料活动区间过滤（版本+runs 的时间戳推出三个活动窗：
  10-01 15:42–17:21、10-02 06:45–07:07、10-02 08:07 前后），得 **331 个请求**。
  ⚠️ 遥测是 profile 级不是会话级：同窗内若有其它并行会话会被计入（本窗口按工作节奏判断污染很小，但非零）。
- **估算口径**（记录生成器写死的启发式）：
  文本 = 字符数 ÷ 3；图片 = 每次出现 1000 token（粗估视觉 token）。
  图片数是**裁剪策略之后**路由真正收到的出现次数（`imagesBeforePrune` 另记原始数）。
- **费用口径**：这里是"token 当量"，各厂商对图片的实际计价与 1000 tok/张的假设必有出入。

## 1. 总量

| 项 | 数值 |
|---|---|
| LLM 请求数 | **331** |
| 文本 token（估算） | **≈ 19,226,843** |
| 图片出现次数（裁剪后） | **22,221 次** → ≈ 22,221,000 token 当量 |
| **合计** | **≈ 41.4M token 当量** |
| 单请求均值 | ≈ 125,220 |
| 总高载请求（>300k 当量） | 63 个 |
| 历史裁剪（compaction） | 2 次 |

**单看最后一条请求的上下文体积**（≈ 会话记忆的终态）：文本 ≈ 75k token + 携带 288 张图。
也就是说：**会话结束时的记忆里躺着近 300 张图**——每一轮新请求都要为它们付一遍视觉 token。

## 2. 图片 vs 文本：五五开，图片是第一消耗

- 图片 22.2M ≈ **54%**，文本 19.2M ≈ 46%。
- 331 个请求里 215 个带图；**116 个纯文本请求的中位文本就有 66k** ——哪怕这一轮一个图都不带、
  只是在量尺寸或讨论，整段历史（含图片占位文本）照单重放，这就是"上下文用得快"的机制：
  **成本随轮数二次累积**（历史变长 × 每轮都要付）。

## 3. 两条路由的裁剪策略差距是最大单一发现

| 路由 | 请求数 | 带图请求的图片数 | 原始图次 | 裁剪率 |
|---|---|---|---|---|
| `deepseek-*`（原生，计数预算 ≤24 张） | 148 | **中位 21，最大 24** | 19,183 | **84%** |
| `glm-*`（pi-ai，字节预算 2.5MB/请求） | 183 | **中位 296，最大 309** | 19,524 | **2%** |

两条链在同一个下午跑了同一个项目，图片负载差 **10 倍以上**。根因：pi-ai 侧按
`maxRequestImageBytes=2.5MB` 裁剪，而经过 DSH 归一化/缩放后的图很小——2.5MB 装得下 **300 张**，
字节预算形同虚设；deepseek 侧按"保留 24 张"计数裁剪，工作正常。glm 那 67 个带图请求
平均扛着 ~287 张图（≈ 287k 视觉 token 当量/请求），是"上下文烧太快"的最大单一来源。

> 上一轮已经给 `generate_part` 加了 `views` 参数（数值迭代只挂 1 张），在 deepseek 侧每次生成立省 3 张；
> 但 glm 侧的根本问题在预算单位，参数救不了——需要把 pi-ai 的裁剪改成计数制（对齐 24 张）。

## 4. 阶段分解（按语料里程碑时间切，粗粒度）

| 阶段 | 请求 | 文本 | 图片出现 | 图 token 当量 |
|---|---|---|---|---|
| M1 骨架 | 12 | 326,875 | 256 | 256,000 |
| M2 调焦（齿形返工在此） | 54 | 2,105,407 | 1,086 | 1,086,000 |
| M3 光学 | 5 | 232,414 | 104 | 104,000 |
| M4 稳定性 | 46 | 2,481,857 | 929 | 929,000 |
| 收尾/修复/续作 | 165 | 10,488,065 | 6,013 | 6,013,000 |
| （另一路由的其余请求） | 49 | 3,592,225 | 13,833 | 13,833,000 |

要点：**收尾阶段（改错、复检、报告）比设计本体烧得还多**——这正是历史最长的时候；
M2 的齿形返工（14 个返工版本）贡献了显著的一段。前 28 个请求累计已达 ≈0.85M 文本，
每 28 个请求文本累计翻倍式上涨（0.85 → 1.97 → 3.34 → 4.88M …）。

## 5. 图片从哪来（语料侧账本）

| 来源 | 次数 | 说明 |
|---|---|---|
| `generate_part` 渲染 | 50 版本 × 4 视图 = 200 张 | 本轮已加 `views` 参数可省 |
| `validate_assembly` 装配图 | 每次 3 张 × 多次复检 | |
| `simulate_physics/motion` 关键帧 | 每次 ≤4 张 | |
| `measure_closest` 标注图 | 每次 1 张 | |
| 用户截图（对话框） | 若干 | 走附件通道，模型上下文保留引用 |

单次挂图不多，但**不裁剪地留在历史里、然后每轮重放**，才是真正的账。deepseek 侧的
"保留最近 24 张"策略把 19,183 次出现裁到 3,007 次，效果已被数据证明。

## 6. 建议清单（按杠杆排序）

1. **pi-ai 裁剪改计数制**（对齐 deepseek 的 24 张，或两者取小）——本报告最大发现的修复点，
   预计把 glm 侧图片负载砍 ~85%，整体 token 当量降约三分之一。改 `image-budget.ts` 一处。
2. **数值迭代用 `views:["iso"]`**（已上线，skill 已教）：一次 generate_part 省 3 张。
3. **长收尾阶段主动开新会话**：收尾/修复段的单位请求成本是全程最高（历史最长）；
   交付报告用新会话 + 语料自描述（manifest/check 报告都在磁盘上）几乎零成本重建上下文。
4. **DSH 侧**（上轮已提，与 P2-11 同源）：`offloadRequestImagesWithPolicy` 若能按
   "信息量分级"（用户截图 > 工具渲染图）裁剪，在同样预算下保留更多有效信息。
5. 遥测可加一个 `purpose: 'cad-tool'` 的粗分类字段，下次这类报告能把"工具结果文本"与
   "对话历史"拆开量化（本轮只能给文本总量）。

## 7. 一句话结论

microscope3 全程 ≈ **41.4M token 当量 / 331 请求**；其中图片占 54%，而图片负担集中在
**glm/pi-ai 路由的字节预算失效**（单请求最多扛 309 张图，裁剪率仅 2%）——把它改成与
deepseek 相同的计数裁剪，是现有系统里最大、也最容易吃到的一项节省。

## 8. 追记：参考图事件的归因（2026-10-03 复核）

用户问"成品与示例图差很大，图是不是没传进去"。遥测裁决：

- **传进去了**：首轮请求携带 6 张图（含用户参考图）；
- **但 4 分钟就被裁了**：第 15 个请求（15:46:39）首次触发裁剪，最老优先——
  **用户参考图是全场最老，所以第一个出局**；此后 ~300 个请求模型都没有再看它；
- 10-02 续作会话开头 290 张图里全是工具渲染图，参考图根本不在场。

修复：offload 策略新增 `protectUserImages`（user 消息顶层图片豁免，
tool 渲染图照常可裁），详见 DESGIGN.md §14.5。这是 §6 建议清单第 4 条的落地，
并且比"分级裁剪"更进一步——用户附件不参与预算，直接免裁。

## 9. 更正（2026-10-03 晚，沙盒复核后）

§8 所记的 `protectUserImages` 修复**在现货 dsh（0.2.0-rc.2）上不存在**：
`dsh-compaction-image-offload` 的 `offloadOldestImages` 对 user 消息与
tool-result 一视同仁、最老优先，没有用户图豁免；且 dsh 升级会覆盖直接打在
vendor bundle 上的改动。本报告 §3/§8 中"参考图可豁免"的结论在当前环境不成立——
在豁免真正回到宿主内核之前，请按"参考图仍会被最老优先裁掉"对待，
缓解手段是长会话主动开新会话 + 把参考图要点写进文本。详见 DESGIGN.md §15。

## 10. 再更正（同日晚，插件内受保护执行器上线）

§9 的局限已被插件侧方案补上（DESGIGN.md §16）：本插件的 bundle patch 停用
现货 `image-offload` 行，由插件内受保护执行器接管同一 `image/offload` 接缝，
**user 消息顶层图片永不入选**，tool 渲染图照常最老优先。参考图豁免自此在
插件内成立且升级免疫（dsh 升级只可能使接缝形状漂移，验收脚本会红而非静默）。
"缓解手段"降级为备份：召回工具 `recall_reference_image` 仍在，长会话开新
会话依然是好习惯。
