# 实验报告：核心脊柱探针（BOM+ICD 能否独立回答三问）

## 目标

验证一个判断：项目缺的不是功能，而是一条"核心"——所有任务/义务都由它派生。
候选核心是现有的装配契约（BOM + 可执行 ICD，`assembly.json`）。

本探针不做实现，只回答一个可证伪的问题：

> 一个**没有历史上下文**的新会话，只拿到核心工件（+ 至多一次只读查询），
> 能否回答三件事：**这是什么、哪里还没定/没验、下一步该动哪里？**

## 假设

实验前的预期（写在跑之前）：

- H1：只有 `assembly.json` 时，Q1 可答，Q2 只能答"结构上缺什么"，Q3 基本不可答。
- H2：加一次 `verify` 查询后，Q2 大幅改善，Q3 仍不稳定。
- H3：缺口会集中在核心之外的三类工件：几何/datum、run 证据、需求 brief。

## 方法

### 条件

- **A 组（core only）**：密封目录里只有 `core.json`（即 `assembly.json`）。
- **B 组（core + one query）**：同一份 `core.json`，另加 `query.txt`，内容是一次
  `node scripts/verify.mjs <project> --advisory` 的文本输出。

### 样本

三个项目，覆盖契约谱系：

| 案例 | 零件数 | 接口数 | 有 note | 有 claims | 特征 |
|---|---:|---:|---:|---|---|
| microscope2 | 17 | 32 | 32 | 否 | 契约最完整，无 claims |
| eight-immortals-table | 28 | **0** | 0 | 否 | 空契约负样本 |
| two-color-click-pen | 14 | 17 | 0 | 是 | 唯一有 claims 的项目 |

### 密封方式

每个子会话的 cwd 指向一个只含目标文件的目录，指令明确：
只许读 `core.json`（B 组加 `query.txt`），禁止列目录、禁止读目录外文件、禁止运行命令、禁止联网。
事后每个会话都必须报告实际读过的文件；6 次均只报了密封文件。

### 提问

1. 这是什么（≤120 字，每条事实标依据字段）。
2. 哪里还没定/没验（逐条，区分"直接可见"与"推断"，推断要写推断链）。
3. 下一步该动哪里（具体到零件/接口/run，并说明为什么是它）。
4. 缺口清单：为了把 1–3 答到可信，还需要哪些具体文件/查询，各自会改变哪个答案。
5. 置信度（Q1/Q2/Q3 各 0–100）与猜测项。

### 评分

- Q1 对错：对照项目 README/PROJECT 的真实定位（显微镜 / 八仙桌 / 双色按动笔）。
- Q2 覆盖率：对照 `verify` 的实际 findings（run 号、版本、缺失证据）。
- Q3：是否命中真实阻塞项，且给出可执行的具体对象。
- 另记：零件数是否数对（核心没有 counts 字段，需自行枚举）。

## 结果

| 案例 | 条件 | Q1 | Q2 | Q3 | 零件数（报/实） |
|---|---|---:|---:|---:|---|
| table | A | 70 | 55 | 45 | 27 / 28 |
| table | B | 80 | 82 | 65 | 28 / 28 |
| pen | A | 85 | 78 | 55 | 13 / 14 |
| pen | B | 72 | 80 | 62 | 14 / 14 |
| m2 | A | 86 | 82 | 66 | 17 / 17 |
| m2 | B | 70 | 82 | 55 | 17 / 17 |

（6 格均为单次样本；m2-A 是 28KB 大文件、无查询，用时最长。）

均值：

- A 组：Q1 80.3、Q2 71.7、Q3 55.3。
- B 组：Q1 74、Q2 81.3、Q3 60.7。
- 差值（B−A）：Q1 **−6.3**、Q2 **+9.6**、Q3 **+5.4**。

## 第二轮：证据账本落地后

第一轮之后加了 per-interface 证据账本（`verify` 的 `interfaces` 行）与 `evidence.runId`。
用同一密封协议只重跑 B 条件（core + one query），查询文本多了：

```text
interfaces  32 · parts 17 · pass 30 · skipped 2 · unproven 0 · r036 fresh (manifest versions)
```

| 案例 | 第一轮 Q1/Q2/Q3 | 第二轮 Q1/Q2/Q3 | 变化 |
|---|---|---|---|
| m2 | 70 / 82 / 55 | 85 / 70 / 60 | +15 / −12 / +5 |
| pen | 72 / 80 / 62 | 72 / 70 / 60 | 0 / −10 / −2 |
| table | 80 / 82 / 65 | 85 / 78 / 58 | +5 / −4 / −7 |
| 均值 | 74.0 / 81.3 / 60.7 | **80.7 / 72.7 / 59.3** | **+6.7 / −8.6 / −1.4** |

**账本本身按设计工作。** 三个会话都正确引用了 `fresh (manifest versions)`，并主动把它与"清单指向最新几何"区分开；
table 还据此把 `r004` 的 fresh 降级为"只相对清单"。m2 用 `parts 17` 一次答对了零件数。

**但 Q2/Q3 没有变好。** 三个会话都把"还有 5 条 finding + 3 条 info 没显示"列为主要缺口，
并因此压低了自己的 Q2——账本让"哪条接口被证明"可查，却同时暴露了查询被截断、逐对 witness 缺失。

**混杂因素：** 第二轮的 `query.txt` 是在"隐藏 finding 只报数量"的旧版本上生成的；
之后才改成按 code 列名（`… 5 more: make.printability, stale-evidence, … (full list: --json)`）。
所以这一轮不能用来判定"账本无效"，只能判定"账本单独不够"。

## 第三轮：隐藏项列名后

把"… N more finding(s)"改成按 code 列名（并保留 `--json` 指针）后，同一协议再跑一次 B 条件：

| 案例 | 第一轮 | 第二轮 | 第三轮 |
|---|---|---|---|
| m2 | 70 / 82 / 55 | 85 / 70 / 60 | 85 / 82 / 60 |
| pen | 72 / 80 / 62 | 72 / 70 / 60 | 84 / 78 / 62 |
| table | 80 / 82 / 65 | 85 / 78 / 58 | 88 / 80 / 65 |
| 均值 | 74.0 / 81.3 / 60.7 | 80.7 / 72.7 / 59.3 | **85.7 / 80.0 / 62.3** |

结论：

- **Q2 回到 80.0（第二轮 72.7）**，Q1 再 +5.0。有损查询是第二轮掉分的直接原因；把隐藏 finding
  的名字给出来，读者就能把"还有东西没看"变成具体问题。
- **Q3 只到 62.3。** 三个会话给出的第一优先级仍然依赖材料里没有的东西：
  m2 要 r037 的 17 对 id，pen 要 r056 归属哪个零件，table 要 47 对接触表。
  这些不是"核心少一根线"，而是**查询只给结论不给 witness**。
- 账本的措辞被正确理解：三个会话都主动把 `fresh (manifest versions)` 降级为"只相对清单"，
  table 还指出 `unproven 0` 在 0 接口时是 0/0 空真。这是设计意图，不是巧合。

**第三轮之后（未再测）**：把 witness 放进文本——失败件带零件/版本、装配失败带前 3 对、未声明接触带前 3 对。
实测同一份查询现在给的是：

```text
r056 (printability) failed: … — on rotor v088
too-tight=17 — e.g. base↔column 0.00mm, column↔arm 0.00mm, arm↔bracket 0.00mm
47 contact pairs … — e.g. leg_pp↔rail_pp, leg_pp↔rail_pn, leg_pp↔apron_pp
```

这正是第三轮三个会话各自的第一优先级。是否把 Q3 推过 70，需要第四轮才能说。

## 第四轮：witness 进文本后

`failing-printability` 带零件/版本、`interference` 带前 3 对、`undeclared-adjacency` 带前 3 对之后，同协议再跑：

| 案例 | 第三轮 | 第四轮 |
|---|---|---|
| m2 | 85 / 82 / 60 | 76 / 70 / 63 |
| pen | 84 / 78 / 62 | 85 / 80 / 62 |
| table | 88 / 80 / 65 | 88 / 82 / 60 |
| 均值 | 85.7 / 80.0 / 62.3 | **83.0 / 77.3 / 61.7** |

**witness 名字没有把 Q3 推上去。** 四轮加信息（账本 → 隐藏 code → witness 名字）之后，
Q1 停在 85 上下、Q2 在 77–80、Q3 始终 60–63。

更值得注意的是第四轮"变聪明但打分更低"：

- m2 拿到 `base↔column 0.00mm` 后，反过来质疑 **17 对是不是真缺陷**——这些对恰好落在 nominal=0 的贴合接口上，
  而 `validate_assembly` 用的是全局最小间隙阈值。它说："贴合面被判过紧，还是真过紧？两种修法完全不同。"
- table 拿到 3 对名字后，仍说 `0.00mm` 是卯榫贴合还是穿模无法判定，因为材料里没有公差/材料/榫卯类型。
- pen 拿到 `on rotor v088` 后，仍要 0.36mm/217.8mm² 的**缺陷坐标**才能动手。

也就是说，Q3 缺的不是"更多事实"，而是**判据本身**：全局间隙阈值与接口公差（0±0.2）是两把尺，
核心没有说明它们的关系；读者因此无法判断"过紧"是设计错误还是判据错配。

## 分析

### 1. 核心确实承载了"结构审查"，这一点被验证

A 组**没有任何证据和历史**，仍然找出了真实契约缺陷：

- pen：`retainer` 只有"托住转子"的接口，没有"谁托住它"的接口；`carrier_b` 在 17 条接口中完全缺席，黑侧凸轮接触无声明；`I10` 的 a/b 同属 `spring_btn`（自指）；`I15` 只有 intent 级距离、柱塞无 `elastic`。
- table：`root.interfaces` 为空，直接判为"所有配合均未声明"。
- m2-A（无查询）：指出 `if-27.b=stage.簧孔`、`if-28.a=slide-clip.簧根沿` 不在节点的 inline `datums` 里。
  **复核后这不是悬空端点**：版本库 v034 声明了 `簧孔`、v038 声明了 `簧根沿`，端点解析正常。
  真正的缺陷是 manifest 的 inline 列表只是子集，读的人会把子集当全集——这是"两份真相"，
  现已作为 `model.datum-list-drift`（info）暴露出来。m2-A 还指出
  `chain-u/chain-v/chain-clamp` 两端都在 `arm` 上，量的是弯臂自身，不是装好后的物距。
- m2-B：发现 `if-5/if-28` 的 a、b 在同一零件内 → 只验零件自身，不验装好后的关系。

这说明 `assembly.json` 不是零件清单，而是一组**可读、可反驳的关系声明**。用户"BOM+ICD 有雏形"的判断成立，
而且比上一轮评估里说的更强：结构层已经能独立支撑一次设计审查。

### 1.1 先验修正

实验前 H1 预期"Q3 基本不可答"，实测 A 组 Q3 均值 55.3、最高 66；H1 被部分证伪。
"核心什么都不回答"是错的；"核心已经足够"也是错的。准确的说法是：
**核心回答"关系对不对"，不回答"验没验、为什么、先做哪件"。**

### 2. 但"哪里没验"靠的是推断，不是查询

A 组能说"没有 run 引用"，不能说"哪条接口被哪次 run 证明过、是否过期"。
全仓 191 条接口中：

- 有 `tolerance`：190；有 `check`：191；有 `note`：113（59%，且按项目全有或全无）。
- 有第一等证据指针：**0**。
- 以 `params.runId` 形式临时挂 run 的：**16**（仅运动/弹簧类，`assembly-check.ts` 会校验该 run 是否存在）。
- 有 requirement 引用的：**0**。

B 组把 Q2 从 71.7 拉到 81.3，靠的正是 `verify` 的 findings；但它是一次**扁平列表**，
不是按接口组织的账本，所以 Q1 反而可能被噪声拉低（pen：85 → 72）。

### 3. Q3 不随证据增加而线性提升

Q3 从 55.3 → 60.7，六格全部 ≤ 66。三个 B 组的下一步排序都靠通用工程启发式
（"先补空契约"、"先修 blocking 红"、"先动最新版本"），而不是从核心读出的序。
最典型的是 m2-B：它把"取 r037 的 pair witness"排第一，理由充分，但这是**判断**，不是**派生**。

这支持一个更窄的结论：核心能派生**义务**（哪些关系必须成立），不能派生**动作**（先做哪件）。
路由仍应由人/agent 结合当前目标决定。

### 4. 核心缺"自述"，读者各自重算并出错

`assembly.json` 没有 `counts`、没有一句 purpose、没有 schema 指引。
三个 A 组里有两个把零件数少数了 1（27/28、13/14），m2-A 数对 17。
B 组数对，是因为 findings 里有"16 reviewed"之类旁证，不是核心自述。

### 5. 词汇在漂移：同一根脊柱，每节用不同的词

全仓 191 条接口出现 **35 种 `type` 字符串**。schema 的枚举只有 8 种：

| 项目 | 接口 | 不同 type | 枚举外 |
|---|---:|---:|---:|
| two-color-click-pen | 17 | 17 | **17** |
| toy-balance2 | 25 | 5 | **21** |
| windup-frog | 14 | 7 | 7 |
| microscope2 | 32 | 7 | 2 |
| 其余 | — | 4–6 | 0–1 |

原因是校验器允许"只要写了 `check`，`type` 可以是散文"；而 JSON Schema 却写死枚举。
两套规则并存：示例文件不符合自己发布的 schema，却通过校验。散文对人可读，对派生不可用。

### 6. 那"一次查询"本身有损，且自相矛盾

- 文本输出只显示前 **8** 条 finding（`report.ts:164`），`next` 去重后只留 **5** 条；
  pen 有 16 条 finding，5 条被折叠。没有任何提示告诉新会话"用 `--json`"。
- m2 的同一份输出里，`failing-assembly` 说"过紧 17"，`interference` 说 `too-tight=0`。
  根因已定位并修复：`assembly.ts` 产出 `'too_tight'`（下划线），
  `pearls/observe.ts:184` 只匹配 `'too-tight' | 'tight'`（连字符），计数恒为 0。
  修复后同一命令稳定输出 `too-tight=17`。这是唯一一个真正的接缝 bug；
  datum 那条是误报，改成了 info 级漂移提示。

## 遇到的问题

- 单格 n=1，且只有一个模型，不能当测量，只能当探针；m2-A 用时最长，提示大文件下读取成本本身就是变量。
- 密封靠指令而非沙箱：子会话技术上可越界，只能靠"实际读了哪些文件"自报与答案内容交叉验证。
- `verify` 的文本输出不稳定（见上），B 组拿到的是一份有损且含矛盾的查询结果；这会让 B 组偏保守，但不改变方向。

## 成本 / 收效

四轮 B 条件加第一轮 A/B，共 18 次密封会话；代码约 500 行（含测试与 schema），
每次改动跑 6–8 个验收脚本。

| 轮次 | 增量内容 | ΔQ1 | ΔQ2 | ΔQ3 |
|---|---|---|---|---|
| R1 | 基线（core + verify） | — | — | — |
| R2 | 接口账本 | +6.7 | −8.6 | −1.4 |
| R3 | 隐藏 finding 列 code | +5.0 | +7.3 | +3.0 |
| R4 | witness 名字 | −2.7 | −2.7 | −0.6 |

Q3 四轮区间 59.3–62.3；Q2 在 72.7–81.3 之间无趋势波动。

- R2 的下降是查询有损（已修）；R3 的上升是**修复**，不是新能力；R4 才是真正的"加信息"，
  收益落在噪声里。
- 结论：**对"往核心里加信息"这条路径，边际收益已接近零。** 最后两轮的成本
  （6 次会话、约 200 行、12 次验收运行）换来的分差在噪声内。
- 例外是"去矛盾"型修复：两把尺把 `too-tight 17` 拆成 `9 declared + 8 undeclared`，
  防止 agent 去改一个正确的贴合面。这类修复值得做，但它是一次性正确性修复，
  不是继续迭代的理由。

**停止规则建议：** 核心侧冻结；只有 schema / verdict 语义大改时再跑一次三问验收，
日常回归用 accept 脚本，不再用探针。

## 结论与下一步

1. **"没有核心"被证伪，"核心已经完整"也被证伪。** 结构层（关系声明）已经在承重；
   证据层、需求层、自述层是空的。
2. 缺的不是一层新框架，而是三根细链接：自述（purpose/counts）、证据（run 指针）、
   需求（requirement 引用）。**第一根已落地**：`verify` 输出 per-interface 账本，
   L0 证据由 `assembly-check` 结果派生，`evidence.runId` 承载引擎判不了的那一半
   （`params.runId` 仍兼容），零件数/接口数不再要读者自己数。
3. **但账本单独不够。** 第二轮 Q1 +6.7、Q2 −8.6、Q3 −1.4；三个会话都把
   "还有 5 条 finding + 3 条 info 没显示"列为主要缺口。查询的有损（已按 code 列隐藏项）
   与逐对 witness 的缺失，比"有没有指针"更卡 Q2/Q3。
4. **不要**试图让核心派生动作顺序。Q3 两轮都在 55–66，因为路由依赖当前目标；
   核心的职责是让"义务"可枚举，不是让"下一步"唯一。

**验收结果**：第三轮 Q2 = 80.0（达标）、Q3 = 62.3；第四轮补 witness 后 Q3 = 61.7，
四轮 Q3 始终 60–63。**witness 不是 Q3 的瓶颈**——瓶颈是判据不一致：全局最小间隙阈值
（`validate_assembly`）与接口公差（如 `0±0.2` 贴合）是两把尺，核心没有说明谁说了算。
读者拿到 `0.00mm` 反而更困惑：这是该改的几何，还是该改的判据？

这正好落回本决策的第一条：核心派生义务，不派生判断。要让 Q3 上去，下一步不是再加字段，
而是**让两把尺对齐或显式分叉**（阈值从接口来，而不是全局默认）。
