# 实验报告：0.2.0 工具面固定前缀与 token 预算（Q1）

## 目标

给「CAD 请求的固定前缀」一个可复跑的数字和一条预算线，回答两件事：

1. 9 个 surface 之后，模型每轮固定要读的插件侧前缀到底有多大？
2. 以后加工具/加技能时，怎么在 CI 里发现它悄悄变大了？

## 假设

- 切到 9 个 surface 后，固定前缀应从「几十个工具 schema」降到约 1–2k token；
- 前缀的绝大部分由工具 schema 与 skill 目录描述构成，skill 正文按需加载、不该计入；
- 一旦有基线，新增一个工具带来的增长是可见的（而不是等到某次会话变慢才发现）。

## 方法

脚本：`dsh-cad-harness/scripts/accept-token-budget.mjs`（2026-11-27 新增，已进 `accept:preview`）。

测量口径（写死在脚本头注释里，避免以后各说各话）：

| 组成 | 怎么量 | 是否计入固定前缀 |
|---|---|---|
| 9 个 surface 的 schema | 用假 ctx 注册 9 面（`hideLegacy: 全部`），取 `name + description + parameters` 的 JSON 字符数 | 是 |
| skill 目录条目 | `skills/*/SKILL.md` 的 frontmatter：`name + description + whenToUse` | 是 |
| skill 正文 | 同上文件的完整字符数 | **否**（只有被 `skill` 工具加载时才进上下文） |
| 对话历史 / 宿主指令 / AGENTS.md | 不量 | —（不属于插件可控范围，Q1 明确只承诺插件侧） |

预算（脚本断言）：

- 9 面 schema ≤ **6144 chars**（与 `docs/TOOL-SURFACE-V1.json` 的 `schemaCharsBudget` 同一数字）；
- 固定前缀 ≤ **基线 × 1.10**（基线存 `dsh-cad-harness/docs/TOKEN-BASELINE.json`）。

## 结果

2026-11-27 实测（本机，`node scripts/accept-token-budget.mjs`）：

| 项 | 字符 | ≈token（chars/4） |
|---|---|---|
| 9 面 schema | 4,065 | 1,016 |
| skill 目录（5 条） | 1,865 | 466 |
| **固定前缀合计** | **5,930** | **1,483** |
| 对照：45 个旧工具 schema | 104,675 | 26,169 |
| skill 正文（按需，不计入） | 49,831 | — |

- 相对旧工具面降幅 **94.3%**（104,675 → 5,930 chars）。
- 9 面单面最大 546 chars（`cad_inspect`），全部在 6144 预算内。
- 与 2026-11-26 决策记录里的 101,573 chars（44 工具）相比，旧面因为新增
  `scan_stress_hotspots` 涨到 104,675 —— 这正是「没有预算就没人发现」的例子。

复现：

```bash
cd dsh-cad-harness
node scripts/accept-token-budget.mjs            # 门禁
node scripts/accept-token-budget.mjs --json     # 机器可读
node scripts/accept-token-budget.mjs --write    # 记录/更新基线（会打印 delta）
```

## 分析

- 假设成立：前缀已经降到 ~1.5k token，其中 68% 是工具 schema、32% 是技能目录。
- **「削」的空间不在工具上，而在 skill 目录描述上**：5 条描述占 1,865 chars，
  平均 373 chars/条。继续加压收益有限（再削一半也只省 ~230 token），但会伤可发现性，
  因此 Q1 到此为止——目标是「不回归」，不是「越小越好」。
- 旧面 104,675 chars 说明这类漂移是持续的：只要没有基线，每次加工具都在无声加税。

## 遇到的问题

1. **口径之争**：一开始想量「整段上下文」，但对话历史、宿主指令都不在仓库里，
   量了也只反映某次会话。最终口径定为「插件侧固定前缀」，并在脚本头写清排除项。
2. **`accept-skill-tools` 里的字面量计数**：skill 写着「44 ops」、脚本断言「39 ops」，
   而注册表已是 45 —— 与 Q2 修的 surface 计数是同一个病。已改为「解析 skill 里写的数字
   并与注册表比对」，不再写死总数。
3. **skill 目录的 frontmatter 解析**：只是一行行 `key: "value"`，没有引入 YAML 依赖。

## 结论与下一步

- 固定前缀已降到 5,930 chars，9 面 schema 在预算内；基线已入库，`accept:preview` 会守。
- **未完成（Q1 出口的另一半）**：3 个代表任务的 A/B 报告——同 brief、pass 不变、
  token 降幅 ≥20%。这部分需要真实会话：
  - A 组：旧工具面（`toolSurfaces` 关闭，45 个工具）；
  - B 组：9 面（生产配置）；
  - 记录每组的实测 token（宿主侧计费口径）与任务通过情况；任务建议取
    「单件 bracket：生成→打印检查」「三件装配：契约→运动」「流体管道：预设→收敛」。
  - 说明：本报告只证明了**固定前缀**的降幅（94.3%），没有把它冒充成端到端 token 降幅。
