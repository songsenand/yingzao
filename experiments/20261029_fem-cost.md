# 实验报告：`simulate_stress` 的时间成本（全件 vs 细化）

## 目标

回答两个互相矛盾的说法：全件 FEM 到底是“秒级”还是“成本高”？测出默认网格与细化网格的真实耗时，给“交付前必跑”的分层策略提供数据。

## 假设

- 默认网格（最薄方向 8 个单元）下，全件是秒级到一分钟级；此前“全件 FEM 成本高”的说法只在**可信细化网格**下成立。
- 时间不只随零件尺寸增长，更随**实体单元数 × CG 迭代数**增长；默认网格对厚件可能粗到不可信。

## 方法

- **全件**：果糖项目 41 个版本（`v001`–`v041`），逐件调用 `simulate_stress`。
  - `dxMm` 用工具默认值（最薄方向 8 个单元）。
  - 通用工况：`supports: [{face:{axis:'z',side:'min'}}]`，`loads: [{forceN:[0,0,-1], face:{axis:'z',side:'max'}}]`（1 N 压缩，仅用于计时，不是真实工况）。
  - `mode:'scan'`，`runConvergence:false`。
  - 在 `execute` 外层用 `Date.now()` 测墙钟；从返回的 `method` 取 `dxMm` / `gridCells` / `solidCells` / `cgIterations`。
- **细化**：B03（v016）、C3（v001）、H（v013）、天平 panL（v007）、天平 base（v001），指定 `dxMm` 重跑；B03 另测 `runConvergence:true`。
- 环境：本机，Node 26，Python worker，单进程；运行时根目录指向 `.tmp-motion-rerun/runtime`。

## 结果

### 全件默认网格

| 指标 | 数值 |
|---|---:|
| 版本数 | 41（40 成功，1 拒绝） |
| 总耗时 | **31.3–31.6 s**（两次运行） |
| 中位数 | **0.73 s/件** |
| p90 | **0.81 s/件** |
| 最慢 | **3.48 s**（v001，含首次 worker 启动） |
| 热态最慢 | ~0.9 s |

失败件：`v038`，`the mesh is not watertight — a voxel FEM needs a closed mesh`。拒绝是正确行为，不是计时失败。

### 细化网格

| 零件 | dx (mm) | 实体单元 | CG 迭代 | 墙钟 |
|---|---:|---:|---:|---:|
| 果糖 B03 | 0.8 | 2,986 | 553 | 15.3 s / 7.1 s |
| 果糖 B03 + `runConvergence` | 0.8 | 2,986 | 553 | 13.9 s / 6.1 s（+conv 未显示稳定 overhead，无法从这两次分离） |
| 果糖 C3 | 2.0 | 1,733 | 531 | 9.2 s / 4.1 s |
| 天平 base | 2.0 | 8,011 | 1,939 | **41.5 s / 50.2 s** |
| 天平 panL | 0.5 | 66,212 | 622 | 16.5 s / 12.4 s |
| 天平 base（默认） | **10.0** | **17** | 50 | 0.43 s |

“第一次 / 第二次”是同一台机器、同一工况的两次运行；冷/热、系统负载和可能的缓存会让同一 case 相差接近 2×。**不要用单次值做预算**；下表的时间是量级，不是精确 SLA。

最后一行是反例：base 默认 dx=10 mm，整个件只有 **17 个实体单元**；0.43 s 的结果是粗块，不是应力。默认网格是筛查，不是可信分析。

## 分析

- **“秒级”成立**：默认网格下 41 件总共 31.6 s，中位数 0.73 s；首件 3.48 s 主要是一次性 worker 启动。
- **“成本高”只在可信细化下成立**：单件约 7–50 s（两次运行；冷/热与系统负载可致 ~2× 波动）；按 10–40 s/件估算，41 件全细化约 **7–27 分钟**（大件更久）。
- 时间主要随 **实体单元数 × CG 迭代数** 增长，不是单纯随 bbox：base 8k 单元 × 1939 CG ≈ 42–50 s；panL 66k 单元 × 622 CG ≈ 12–17 s。
- 默认 dx 是“最薄方向 8 个单元”，对薄件合适，对厚件会粗到不可信；交付门应把“默认筛查”和“可信细化”分开。
- 本实验的工况是 1 N 压缩，**不是自重/重力**；测量时自重体力尚未实现（当天晚些已实现，见 DECISION-LOG 2026-10-29），因此这些时间只代表求解成本，不代表“重力内部应力”的验证结果。
- `runConvergence:false`；工具说明称开启约 +30%，但热态对比（15.3 s vs 13.9 s）受启动/波动影响，未单独测出稳定 overhead。

## 遇到的问题

- 首次调用包含 Python worker 启动（约 2–3 s），批量计时应说明是“含启动”还是“热态”。
- 通用 `z-min` 支撑 / `z-max` 载荷只保证可解，不保证工程语义；薄件/球件的接触斑可能很小。
- 默认网格对厚件（base dx=10 mm）没有工程意义；不能用 0.43 s 的结果下结论。
- v038 非水密被拒，说明“全件跑”必须允许单件失败，并在覆盖报告里点名。

## 结论与下一步

- 默认全件筛查 **~32 s**，可以作为交付前的必跑步骤；细化只给 top-K/高风险件，单件 9–42 s。
- 交付门建议（未拍板）：验“覆盖 + top-K 分诊”，不验热力图的颜色。
- “全件 FEM 成本高”应改为：**默认筛查秒级；可信细化单件十秒级；全件细化分钟级**。
- 真正的瓶颈不是 CPU，是**每件的 load case/supports** 与**分辨率可信度**；没有可信工况的件应标 `notMapped`，不要默认假支撑。
- 后续（已完成 2026-10-29）：`simulate_stress` 已加密度 + 自重体力 + `loadCase` + `ground` 支撑，用悬臂梁自重解析解验证（总重/反力/挠度）；下一步把 stress 场接进 `analyze` 作为 strength 第三层。
