# 实验报告：同一提示词下的 OpenSCAD / CadQuery 质量与验证流程

## 目标

用**同一个设计 brief**分别通过 OpenSCAD 和 CadQuery 走真实的 `generate_part` 流程，比较：

1. 两个内核产出的几何质量（尺寸、体积、面积、水密、壳体、genus、最小壁厚、三角数）；
2. 渲染、datum、STEP 与版本 pin 是否一致；
3. 现有验证流程能否发现“几何合法但设计意图错误”的问题。

## 假设

- 两个内核在明确尺寸/原点/datum 的 brief 下应产生同一零件，差异只在三角化。
- `validateVersionGeometry` 能发现网格/STEP/datum schema 问题，但不能判断“是否符合 brief 尺寸”。
- 同一提示词如果不写清原点，可能暴露内核 API 的原点差异。

## 方法

- Brief：`experiments/artifacts/20261120_kernel_quality/BRIEF.md`。
  - 60×40×6 mm 板，4×Ø4.5 通孔（±22, ±13），四角 R4，单一闭合实体。
  - datum：`top`、`top_plane`、`hole_axis`、`hole`。
  - OpenSCAD 用 `$fn=64`；CadQuery 用 Workplane API。
- 两个实现：`plate.scad`、`plate.py`，均由同一 brief 手写，不是两个不同提示词。
- 运行器：`run.mjs`，通过真实 `generate_part` 工具：
  - 两个独立临时项目，`init_project({defaultKernel})`；
  - `views:["top","iso"]`；CadQuery 额外 `step:true`；
  - 之后调用 `measureVersion` 和 `validateVersionGeometry`。
- 环境：Linux x64；CadQuery 2.8.0 + OCP 7.9.3.1.1（临时 pack，已删除）；OpenSCAD **2026.09.23**（Manifold；旧 2021.01 结果另存为 `result-openscad-2021.json`，便于对比版本选择修复前）；Node 26；bundled Python runtime。

复现命令（pack 与 runtime 路径按机器替换）：

```bash
cd dsh-cad-harness
DSH_CAD_CQ_PACK=/path/to/cadquery \
DSH_CAD_PYTHON_ROOT=/path/to/writable-runtime-root \
node ../experiments/artifacts/20261120_kernel_quality/run.mjs
```

**几何差异：**

- 体积差：0.092 mm³ / 13936.018 = **0.00066%**。
- 表面积差：0.116 mm² / 6143.231 = **0.0019%**。
- bbox 完全一致；genus 都是 4；都水密、单壳体。
- CadQuery 三角数约为 OpenSCAD 的 1.95 倍（B-rep 圆角/孔的三角化更密），不构成质量优劣，只是网格密度不同。
- 最小壁厚采样差 0.008 mm，属于采样/三角化差异，不是设计差异。

## 发现的问题

### 1. 第一次 CQ 实现的 z 原点与 datum 不一致，验证流程没有报错

第一次 `plate.py` 直接 `box(60,40,6)`，CadQuery 的 box **以原点为中心**，所以 bbox 是 z=-3..3；但 datum `top` 仍声明在 z=6。结果：

- bbox 很快就暴露 z=-3..3（`measureVersion`），
- 但 `validateVersionGeometry` 当时 **没有 issue**：datum schema 合法、方向合法、数量正确；
- 渲染/水密/genus 也全部通过。

这说明现有验证流程存在一个真实缺口：**schema 合法 ≠ datum 在几何上位于正确位置**。该错误是“设计意图错误”，不是网格错误。

处置：

- 先把 CQ 实现改为 `.box(...).translate((0,0,3))`，与 SCAD 的 z=0..6 对齐；修复后所有指标一致。
- 新增 `datum_outside_bbox` **warn**：datum 点超出网格 bbox 0.5 mm 以上时提示；不 block（fixture/装配原点可以合法在外），但能让这类错误在 `generate_part` 的 warnings 里出现。
- 新增验收：`accept:step-validation` 覆盖 in-bounds 不警告、越界警告。

证据：`result-wrong-z.json` 保留了修复前的 CQ 结果；`result.json` 是修复后结果。

### 2. 验证流程没有“对照 brief 的尺寸断言”

`measureVersion` 会报告 bbox/体积/面积/genus，但 `validateVersionGeometry` 不核对“60×40×6、孔位 ±22/±13、R4”。两个内核都可以是水密、genus 正确，却不符合 brief。当前流程依赖人或 agent 读测量值再判断，不是自动规格检查。

这不是 0.1.1 的 bug，但属于下一层能力：**requirements/spec checker**（把 brief 的尺寸/位置变成断言），否则“验证通过”只代表网格有效，不代表设计对。

### 3. OpenSCAD 与 CadQuery 的 datum 约定一致，但原点约定需要写进 brief

两个内核的 datum schema/参数顺序一致；差异在建模 API 的默认原点。CQ GUIDE 已写 `.box` 居中陷阱，但 brief 本身只写了“envelope 60×40×6”，没有写“底面在 z=0”。后续同 prompt 对比应显式写：

> bottom face at Z=0; all datums in final world coordinates.

### 4. 验证流程本身的其他观察

- SCAD 无 STEP 时 `step_missing` 是 warn；`generate_part` 会过滤这条：合理，STEP 对 SCAD 是可选。
- CQ `step:true` 会额外写 `model.step` + hash + BRep 元数据；`validateVersionGeometry` 回读并对比 STL，本次通过。
- 两个内核的 `views:["top","iso"]` 都正常；CQ 渲染确实走 STL→OpenSCAD，没有 VTK 依赖。
- `generate_part` 的 first-version wall screen 对两者都给出 ~4.75 mm；采样点略有差异，不是问题。
- 本次 OpenSCAD 已是 2026.09.23 / Manifold；修复版本选择前曾用 2021.01（CGAL）跑过一版，旧结果保留为 `result-openscad-2021.json`。即使同为 Manifold，CQ 耗时仍略短；**不能**把单次耗时当作引擎性能结论。

## 分析

- 在明确原点/尺寸/datum 的前提下，两个内核的几何质量几乎等价：bbox 相同、体积/面积差 <0.002%、都水密且 genus 正确。
- CQ 的优势是原生 STEP/BRep 和更细的圆角三角化；OpenSCAD 的优势是同一套既有渲染/装配路径、无额外 pack。
- 真正的质量风险不在“哪个内核数学更准”，而在**作者是否把 brief 的原点/尺寸/datum 写对**。第一次 CQ 的 z 偏移就是例子。
- 现有验证流程能覆盖网格、STEP、datum schema，但缺“datum 与几何位置”和“brief 尺寸断言”两层；前者已加入 warn，后者建议列为 0.1.2/0.2 的 spec checker。

## 结论与下一步

1. 同一 brief 下两内核的几何质量基本一致；差异主要是三角化密度与 STEP 能力。
2. **验证流程有一个已实证的缺口**：datum 可以 schema 合法但位于几何外；已加 `datum_outside_bbox` warn 和测试。
3. **更大的缺口**是没有 brief/规格断言；建议把“尺寸/孔位/圆角/ datum 位置”变成可执行 spec，而不是靠测量值人工比对。
4. 后续同 prompt 实验应显式固定原点、OpenSCAD 版本和 pack 版本，并在 Windows/macOS CI 上重复同一 brief。
